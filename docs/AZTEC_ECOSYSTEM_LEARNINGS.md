# Aztec/Noir ecosystem learnings for Fair Squares

This report distills a sweep of the Aztec/Noir ecosystem at the pinned SDK version (`aztec-nr` / aztec.js **v4.3.0**) for patterns that concretely advance the Fair Squares (FS) contracts. The corpora swept were: **aztec-examples** (prediction-market, gregoswap), **aztec-packages noir-contracts** (amm, orderbook, claim, crowdfunding, app_subscription, auth, auth_registry, token_blacklist, updatable, private_voting, public_checks, schnorr_account), **noir + noir-examples + noir_stdlib**, the **awesome-noir / awesome-aztec** library indexes (zk-kit.noir, noir_sort, noir-bignum, wad.nr, sparse_array, aztec-lint), the **wallet-sdk / demo-wallet** (EmbeddedWallet, BaseWallet, authwit, ECDH crypto), and the **gregoswap** DEX example.

**Methodology.** Each candidate was checked twice: (1) the external symbol/path was opened and confirmed to behave as claimed at v4.3.0, and (2) the corresponding FS file was read to confirm the pattern is genuinely missing (not already implemented and not an explicitly accepted M12–M16 tradeoff). Every line/symbol cited below was verified against the actual source in this repo; nothing here invents an FS field or an external API. Items that turned out to be already-done or deliberate tradeoffs are listed honestly in [§4](#4-explicitly-checked-but-not-recommended). The canonical FS **economic model** (ROR-based rent, pooled pro-rata, small-depositor floor) and **privacy model** (private-by-default, dual-mode) in `CLAUDE.md` are treated as fixed — nothing below contradicts them.

## 2. By subsystem

### DEX (`contracts/fsft_dex/src/main.nr`)

- **Enforce the price band (shortlist #1).** Today `min_price_bps`/`max_price_bps` are computed only in `get_orderbook_snapshot` (`#[view]`, lines 575–589, off `get_valuation_public().last_token_price_bps`). `place_order` asserts only `price_bps > 0`; `_place_and_match` (lines 291–403) never reads the valuation, so a fat-finger or manipulative quote anchored to a stale valuation rests at any positive price. **Change:** in `_place_and_match`, before writing the resting row, read the same anchor (`get_valuation_public().last_token_price_bps`, with the `>0 ? : 10000` par fallback) and `price_band_bps`, then `assert((price_bps >= min_p) & (price_bps <= max_p), "price out of band")` — reusing the snapshot's exact math so the view and the constraint can never diverge. **Nuance:** FS already matches at exact price (`m_price == price_bps`), so a *fill* can't cross outside the taker's price; the band specifically guards a *resting* order. *Source:* amm_contract `_swap_exact_tokens_for_tokens`.
- **Fill-or-kill `min_fill` (shortlist #8).** `place_order` (lines 200–212) has no minimum-fill arg; `_place_and_match` unconditionally rests the unfilled remainder (lines 394–400). **Change:** thread an optional `min_fill: u128` from `place_order` through the `enqueue_self._place_and_match` call (line 274) into the public tail, and `assert(amount - remaining >= min_fill, "min fill not met")` just before "Rest the remainder". `min_fill = 0` preserves today's behavior; the revert unwinds the private-leg escrow so no refund path is needed. The reserved `policy: u8` arg (`let _ = policy;`, line 402) is unrelated and unaffected. *Source:* amm `amount_out_min` / prediction-market `min_shares_out`.
- **Group privately-read config (shortlist #5).** Private `place_order` reads `kyc_verifier` (line 227) plus `fsft_token` (line 237, SELL) or `eur_token` (line 244, BUY) — two separate `PublicImmutable` slots, each a ~4k-gate historical read regardless of width. **Change:** replace the three `PublicImmutable<AztecAddress>` fields (lines 118–120) with one `config: PublicImmutable<Config, Context>` (`#[derive(Packable, Eq)] struct Config { kyc_verifier, fsft_token, eur_token }`) read once per call. (This is the *correct* target for the "group co-read config" pattern — **not** housing_fund, whose private paths verify config in the public tail with cheap SLOADs.) *Source:* crowdfunding `Config`; `public_immutable.nr` / `delayed_public_mutable.nr` grouping guidance.
- **`SingleUseClaim`-backed partial claims (future).** The `OrderOwnerNote` is intentionally NOT nullified on claim/cancel; anti-replay rests on zeroing the per-`owner_tag` claimable balance, with an explicit INVARIANT (lines 253–259) warning any *partial-claim* path must restore anti-replay first. The never-built `terminal_nullifiers: Map<Field, Owned<SingleUseClaim>>` is even specced (`DEX_V3_…SPEC.md:53`). **Change (only when partial claims land):** add a `claim_nullifiers` map keyed by `compute_confirmed_note_hash_for_nullification(confirmed)` **salted with the token/fill dimension** (`poseidon2([note_hash, token, fill_seq])`, *not* bare `(note_hash, owner)` — that would block claiming the second token or a post-fill re-claim). FS already uses this exact primitive in `housing_fund` (`w_withdraw_nullifiers`, main.nr:1161–1162). Do **not** retrofit onto today's whole-balance claim (balance-zeroing already suffices). *Source:* aztec-packages claim_contract; aztec-nr `single_use_claim.nr`.
- **`noir_sort` (future-fit only).** When the reserved `policy` arg implements price-time fill-in-order with price improvement, `sort_advanced` (returns `SortResult{sorted, sort_indices}`, permutation-verified via `get_shuffle_indices`) lets `_place_and_match` constrain that the ≤`MAX_FILLS=4` referenced makers are processed best-price-first rather than trusting the caller's `maker_seqs` order. No change today (a 4-element exact-price loop needs no sort); don't add the dep speculatively. *Source:* `noir_sort/src/lib.nr`.

### Governance (`contracts/governance/src/main.nr`)

- No new standalone governance change is recommended. The privacy posture is already correct: `cast_vote_private` publishes only aggregate yes/no, `vote_claims` are owner-siloed `SingleUseClaim` nullifiers, and the one-vote-per-voter guard (`vote_claims.at(pid).at(caller)`) is the *intended* egalitarian/anti-plutocratic design (`FUTURE_DEVELOPMENT_PLAN.md §4.7`). The M12 revocation handle in the vote tail is addressed by the cross-cutting KYC change below, not by a governance-local edit. (Several governance proposals were checked and set aside — see [§4](#4-explicitly-checked-but-not-recommended).)

### Notes & nullifiers

- **`set_sender_for_tags(recipient)` (shortlist #2).** Discovery tags derive from a `(sender, recipient)` shared secret; the default sender-for-tags is the originating wallet account. `KYCVerifier.issue_credential` (kyc_verifier/main.nr:139) and `ProtocolRewards.allocate_reward_private` (protocol_rewards/main.nr:336) both deliver to a **non-caller** `recipient` without setting it, so in a real multi-PXE deployment the recipient's PXE only finds the note if it registered the issuer as a sender. **Change:** add `use aztec::oracle::notes::set_sender_for_tags;` and `unsafe { set_sender_for_tags(recipient) };` immediately before each `.deliver(...)` (per-call, unconstrained-tagging-only, safe from a constrained context). **Honesty caveat:** this does **not** fail in today's single-shared-PXE demo (the issuer is already a registered sender, per `scripts/e2e/README.md`); it is forward-looking hardening for the V2/testnet multi-PXE direction. Self-delivered notes (`deposit_private`/`reinvest`, recipient == caller) do not need it. *Source:* app_subscription_contract; aztec-nr `oracle/notes.nr:217`.
- **Per-note `MessageDelivery` mode.** All three self-delivered notes use `ONCHAIN_CONSTRAINED`: `deposit_private` (housing_fund:1063/1064), `reinvest_rent_private` (housing_fund:1483/1484), `place_order` (fsft_dex:261/262) — each inserts into the **caller's own** set. For self-delivery the constrained-tagging guarantee buys nothing (mis-delivery only harms the caller). **Change:** downgrade those three to `ONCHAIN_UNCONSTRAINED` (`UintNote.partial()` and crowdfunding receipts do exactly this); keep the two cross-party deliveries constrained. **Honest savings caveat:** at v4.3.0 only the *encryption* constraint gates are removed (a real proving-time win); constrained tagging is a TODO (#14565) and logs are padded equally, so DA/fee savings are currently negligible — the fuller fee win materializes once #14565 lands. Privacy is not worsened. *Source:* aztec-nr `messages/message_delivery.nr`; `uint_note.nr:126`.

### KYC & access control (`contracts/kyc_verifier/`)

- **Private revocation via `DelayedPublicMutable` (shortlist #7).** Today revocation is checked in the public tail via `self.view(kyc.is_credential_revoked(commitment))` (housing_fund:1111, governance:249, fsft_dex:309) over `revocations: Map<Field, PublicMutable<bool>>` (kyc_verifier:60), which forces publishing the constant `poseidon2([owner,nonce])` handle. **Change:** make it `Map<Field, DelayedPublicMutable<bool, REVOKE_DELAY, Context>>` (`revoke_credential` → `schedule_value_change(true)`), and in each private entrypoint read `kyc.revocations.at(commitment).get_current_value()` **inside the private leg** so the commitment is never enqueued. FS already documents this exact fix (housing_fund:1076–1081, `CLAUDE.md` M12); the delta here is that the v4.3 pattern is now verified implementable. **Honest scope:** this **mitigates** M12's consumer-side published handle but does **not "close"** M12/M15 — `revoke_credential` still publicly marks the commitment (DelayedPublicMutable values are public by design), it adds an enforced write-delay (revocations take effect after `REVOKE_DELAY`) and a per-tx expiration-timestamp leak, and M15 (public `verified`/`investor_role` maps/views) is untouched. *Source:* aztec-nr `delayed_public_mutable.nr`.
- **Don't use note-nullification for the revoked-check (design note).** A tempting alternative — revoke by nullifying the credential note, consumers call `assert_note_was_not_nullified_by` — is *anchor-block-only fresh* (`history/nullifier.nr`: "it is not possible to privately prove that a nullifier does not exist by the time a transaction is executed"), so a just-revoked user could still act until the next anchor. **Change:** when implementing M12, add a 2–3 line comment at `revocations` recording **why** the nullifier shortcut is wrong, and prefer `DelayedPublicMutable` whose enforced write-delay + expiration horizon binds tx validity to a provable no-change window. (Both are anchor-block reads; DPM's correctness comes from the write-delay, not from avoiding anchors.) *Source:* aztec-nr `history/nullifier.nr`, `history/note.nr`.
- **Credential expiry (shortlist #10).** `KycCredentialNote` is `{owner, nonce}` with no maturity gate (the affordability covenant's `lock_years` is a different concern). **Change:** add `expires_at: u64` to the note, set it in `issue_credential` (require a real positive timestamp per FS's no-silent-fallback rule — no `0 = never` masking), and after each `assert_note_existed_by` add `assert(header.global_variables.timestamp < confirmed.note.expires_at, "kyc credential expired")` at housing_fund:1048, governance:192, fsft_dex:222 (all already fetch the anchor header). The load-bearing primitive is `get_anchor_block_header().global_variables.timestamp` (**not** `set_expiration_timestamp`, the framework's unrelated tx-expiration call). This is a note ABI + `issue_credential` signature change (re-issue credentials, update the TS harness); it covers only the "aged out" case — explicit admin revocation of a still-valid credential still needs the revocations map. *Source:* aztec-nr `private_context.nr:419`; FS's own DEX block-expiry.
- **Full M12 close-out via zk-kit SMT non-membership (stronger, larger).** Strictly stronger than the two documented M12 fixes: store the revocation set as a Sparse Merkle Tree whose **root** is a `DelayedPublicMutable<Field>`; inside each private entrypoint, read the root and prove **non-membership** of the credential commitment as a *private witness* (`SparseMerkleTree::non_membership(matching_entry, queried_key, index, siblings)`). Then **no** commitment is ever published per action. **Caveats:** admin maintains the SMT + sibling paths off-chain and furnishes them to callers; an empty (zero-root) tree makes `non_membership` a no-op until the first revocation (fine — nothing is revoked yet); choose a multi-hour DPM delay. *Source:* zk-kit.noir `sparse_merkle.nr`; aztec-nr `delayed_public_mutable.nr`.

### Funding / claims / rewards (`contracts/housing_fund/`, `contracts/protocol_rewards/`)

- **`static_assert` the bps ladder (shortlist #3).** `year_emission_bps` is a hand-written `[1300,1200,1100,1000,1000,1000,900,900,800,800]` (main.nr:115–138) that sums to 10000 today but is enforced by nothing on the Noir side (`checkpoint_epoch`'s `distributed + emission <= pool` is a per-call ceiling, not a schedule sum; the `rewardsEmissionParity` Vitest test is TS-side). **Change:** lift the ladder to `global YEAR_EMISSION_BPS: [u64; 10]`, index it from `year_emission_bps`, and add a comptime `static_assert(YEAR_EMISSION_BPS.fold(0, |a,b| a+b) == 10000, "reward bps ladder must sum to 10000 (100% of pool)")`. The conservation property is simply that the 10 yearly slices sum to 10000 (the 12-epoch spread is an orthogonal integer-floor detail — *not* what the assert checks; drop any "×12-weighted" framing). *Source:* `noir_stdlib/src/lib.nr` `static_assert`.
- **M13 remediation — the concrete *how* (large).** M13's leak is the address-keyed public reward maps (`user_claimable` / `user_total_claimed` / `user_last_claimed_epoch`); the *goal* ("move per-user accounting onto the private path") is already tracked, but the **mechanism** is unspecified. Two complementary primitives close it:
  - **(a) Partial `UintNote` completed in public.** `UintNote.partial(owner, context, recipient, completer)` hides owner+randomness privately and returns a `PartialUintNote` whose value is filled in **in public** via `complete(...)` (after asserting the validity-commitment nullifier exists) — exactly for amounts "that cannot be known in private." So `protocol_rewards` can compute the per-epoch share from public emission/weight state in the public tail and settle it into an owner-hidden note **without** address-keyed public balances. FS already uses this commitment pattern in `fsft_dex` claim (`initialize_transfer_commitment` / `transfer_public_to_commitment`), so it's missing from `protocol_rewards` specifically. **Caveats:** the `#[note]`-macro `RewardClaimNote` must migrate to a `UintNote`/`PartialUintNote` shape; this does **not** address M14 (FSFT eligibility is an orthogonal HintedNote ownership-proof problem). *Source:* aztec-nr `uint_note.nr`; orderbook_contract.
  - **(b) Size the reward off a proven `DepositNote` (claim_contract pattern).** Mirror aztec-packages `Claim.claim`: take `HintedNote<DepositNote>`, `assert_note_existed_by`, assert `confirmed.contract_address == storage.housing_fund` and `owner == caller`, bind a per-`(note_hash, epoch)` `SingleUseClaim`, and size the deposit-sub-pool reward (`emission × 40%` × snapshot share) directly off the proven note value — letting FS **delete** the M13 public maps for that sub-pool. FS already proves a cross-contract `DepositNote` in `cast_vote_private` (governance:200–247), so the primitive is in-repo. **Honest scope:** this is a *partial* M13 close-out — it leaves M14 (FSFT sub-pool `balance_of_public`) and the governance sub-pool unaddressed. *Source:* aztec-packages claim_contract + crowdfunding_contract.

### Noir math / correctness

- **Fix the `available_balance` comment (shortlist #6).** `available_balance(deposits, in_defi, allocated) = deposits - in_defi - allocated` (housing_fund:331–335) is documented as having "saturation semantics", but Noir u64 subtraction **reverts** on underflow (proven by `should_fail` tests in `noir_stdlib/src/ops/arith.nr`; `WrappingSub` is the explicit opt-in). The actual fail-closed-revert behavior is the *desired* one — only the comment is wrong (a reader could assume a 0-floor and weaken a guard). **Change:** comment-only; say "reverts on underflow (fail-closed); do not assume a 0-floor." Do **not** add manual range checks — native checked arithmetic already traps (the adjacent note at main.nr:641 already says so). *Source:* `noir_stdlib/src/ops/arith.nr`.
- **Reject noir-bignum / wad.nr (recorded rejection).** FS euro/ROR/emission math is integer `* bps / 10000 [/ 12]` on u128/u64 with magnitudes (€500K acquisition, 8M pool; worst-case products ~1.8e23) far below u128's ~3.4e38 ceiling, and the ROR model is deliberately integer-floored — so arbitrary-width arithmetic (noir-bignum's `udiv_mod` is documented **EXPENSIVE**) or 18-decimal fixed point (wad.nr) would add constraints for zero precision/range benefit. **Action:** record this rejection in `CLAUDE.md`'s math conventions so a future pass doesn't import them. *Optional* low-priority hardening: a `#[contract_library_method] mul_div(a,b,c)` (widen to u128 internally, assert no overflow, divide) for the two u64 `value*bps` / `pool*weight` products that could *in principle* overflow before the divide (protocol_rewards:283, housing_fund:971) — that is mul_div-as-a-pattern, explicitly **not** the libraries. *Source:* noir-bignum `bignum.nr:350`; merkle-groot `wad.nr`.

### Accounts / auth — M16 (`frontend/src/lib/serverWallet.ts`)

- **Aztec-native challenge–signature auth (shortlist #4).** M16's root cause is that one shared server PXE holds every account's keys and routes pick the acting account from request params; `(address, accountIndex)` is **not** authentication. **Change:** add `/api/wallet/challenge` issuing a random short-TTL nonce keyed by claimed address; the client signs an `inner_hash` derived from it with its account key (producing an authwit — the same `createAuthWit` primitive FS already uses at `api/dex/orders/route.ts:235`); the server validates off-chain via the account's `lookup_validity` utility (or a `verify_private_authwit` static-call simulation / schnorr `verifySignature` over `compute_authwit_message_hash(consumer, chain_id, version, inner_hash)`), then binds the session to that address; all routes derive the actor from the verified session. **Two honesty caveats:** (1) the authwit single-use nullifier is only spent when an authwit is *consumed inside contract private execution* — a standalone off-chain verify does **not** auto-prevent replay, so the server must enforce challenge freshness/expiry itself; (2) this closes only the **request→address binding** half of M16 — the **key-isolation** half ("one PXE/key set per session", buildable via `EmbeddedWallet`'s per-instance `store`/`stop()` over `BaseWallet`) is a separate, larger follow-up. *Source:* aztec-nr `authwit/auth.nr`; schnorr_account `is_valid_impl`; wallet-sdk `EmbeddedWallet`/`BaseWallet`.

### Tooling (`.github/workflows/tests.yml`)

- **`aztec-lint` advisory CI job (shortlist #9).** FS CI runs the 77-test suite + Vitest + typecheck but **no static analysis**. NethermindEth's `aztec-lint` (curl-installable Rust binary, SARIF output) implements Aztec-specific lints generic linters miss: AZTEC001 private-data-to-public-sink, AZTEC002 secret-dependent public branching, AZTEC010 `#[only_self]` bridge guard, AZTEC020/021 unconstrained-influence/range-check. **Change:** add a `lint` job (`continue-on-error: true` initially), install a **pinned** tag, run `aztec-lint check contracts … --format sarif`, upload via `upload-sarif`. **Caveats:** (1) **drop the Aztec Test Runner Action** — FS's bespoke `scripts/aztec-test.sh` compile-before-stage-cross-contract-deps ordering is load-bearing (documented in `CLAUDE.md`), and a generic Action would break the governance/protocol_rewards/fsft_dex cross-contract tests; (2) the lint will **flag the documented, accepted M12–M16 leaks** (deposit_private one-bit/amount tail leak, M13/M14/M15 public maps) — suppress those specific lines (`--allow` / inline) so the signal is **new** regressions, not re-flagged tradeoffs. *Source:* awesome-aztec → `aztec-lint` `docs/lints-reference.md`.

## 3. Cross-cutting threads

A few external primitives recur across subsystems — worth noting so the work is sequenced coherently:

- **`DelayedPublicMutable`** is the engine for *both* private KYC revocation (M12) and the M16 authorized-actor read; landing the KYC migration first establishes the pattern in-repo.
- **`assert_note_existed_by` + `SingleUseClaim` keyed by `compute_confirmed_note_hash_for_nullification`** is FS's existing cross-contract-proof idiom (`cast_vote_private`, `housing_fund` withdraw) and is the backbone of both the M13 deposit-note reward (§Funding b) and DEX partial claims — reuse it rather than inventing new keying.
- **Partial `UintNote` completed in public** is the missing piece for any "amount only knowable in public, owner must stay private" flow (M13 rewards); FS already ships it in the DEX claim path.
